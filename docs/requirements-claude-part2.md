# x402 v2 requirements extraction, part 2: `exact` scheme, `exact` on EVM, and the `bazaar`, `payment-identifier`, `sign-in-with-x`, `offer-receipt` extensions

Scope: an independent, spec-only extraction to drive a black-box conformance tester for x402 **resource servers**. Sources are the six Markdown files under `spec/` named in each section; the core specification (`spec/x402-specification-v2.md`) was opened only to resolve cross-references (§5.1 extension shape, §6.1 payment flows, §7.2.1 sidechannel, §9 error codes). No implementation was consulted.

Conventions used in the tables:

- **Role**: `resource server`, `client`, `facilitator`, `any` (spec- or mechanism-level, or all parties).
- **Level**: the exact RFC 2119 word used by the text. `MUST(implicit)` marks prescriptive prose without a keyword; the load-bearing phrase is quoted in the Clause column. `must`/`should` in lowercase in the source are recorded as `MUST(implicit)` / `SHOULD(implicit)` with the phrase quoted. `non-normative example` marks facts only established by an example.
- **Testability** for a resource server (RS) under test: `probe (no funds)` (a 402 fetch, a malformed or throwaway-key request, or a read-only RPC call), `paid (testnet payment)` (a real settlement on a testnet is needed), `facilitator (only if the tool hosts the facilitator)` (observable only from the facilitator side of the RS), `not testable black-box` (obligation on another party, on a document, or on internal state).
- "Throwaway key" means a freshly generated signing key with no funds: it is enough to exercise signature-format, domain and time-window checks, because a verifier rejects the request before any funds are needed.

## Ambiguities and gaps

Scheme `exact` (generic):

1. `maxAmountRequired` (SVM amount exactness) is the v1 field name; v2 `PaymentRequirements` uses `amount`. A tester should compare against `amount`.
2. The client-submitted (payment-proof) family is fully specified in the abstract but no in-scope mechanism (EVM) instantiates it; EXACT-18 to EXACT-28 cannot be exercised against an EVM-only RS.
3. "this specification defines no refund" under `upfront`: failure-after-charge is explicitly unremedied; a tester can only record, not judge, RS behaviour when the handler fails after settlement.
4. `authorization SHOULD be preferred wherever the asset transfer method permits it` has no observable criterion for when `upfront` is justified; only a warning is defensible.

Scheme `exact` on EVM:

5. The `authorization`/`permit2Authorization` field names, types and encodings (decimal strings for `value`/`validAfter`/`validBefore`/`nonce`/`deadline`, 32-byte hex `nonce`) are established only by examples; there is no normative field table. The Permit2 example JSON is not even valid JSON (missing comma, `//` comment, trailing comma).
6. Permit2 verification lists no check that `permit2Authorization.spender` equals the canonical proxy nor that `witness.to == payTo`, although both are described as the security mechanism. The failure codes for these cases are also undefined.
7. Step 2 of Permit2 verification says to "Return `412 Precondition Failed` (Error Code: `PERMIT2_ALLOWANCE_REQUIRED`)". The facilitator `/verify` contract in the core spec returns a JSON `isValid`/`invalidReason`, not HTTP statuses, and the core error-code vocabulary is lowercase snake_case. It is unclear whether the 412 is emitted by the facilitator, by the RS toward the client, or both, and where the code string is carried.
8. Step 4 of Permit2 verification says `permit2Authorization.amount` "covers" the payment (≥), whereas the scheme requires an exact transfer and the proxy transfers `permit.permitted.amount` in full; an over-amount would therefore over-charge. Exact equality is the only consistent reading.
9. No explicit statement that `authorization.to` must equal `payTo` for EIP-3009 (only implied by the core error code `invalid_exact_evm_payload_recipient_mismatch` and by EXACT-13).
10. The EIP-3009 verification does not say how the authorization window relates to `maxTimeoutSeconds` (e.g. `validBefore <= now + maxTimeoutSeconds`); only the Starknet section binds expiry to it.
11. `settlement_pending` is described from the facilitator side only; RS behaviour toward the client (status code, `PAYMENT-RESPONSE` contents, retry semantics) is deferred to the core spec.
12. `extra.assetTransferMethod` is declared "required" for `permit2` and `erc7710` but is unverifiable from the outside: an entry lacking it is, by definition, EIP-3009.
13. The canonical Permit2 address is given only by external link; the proxy canonical address is given inline.
14. The sponsored-approval and EIP-2612 extension documents (`erc20_gas_sponsoring.md`, `eip2612_gas_sponsoring.md`) are referenced but not provided, so Option B/C behaviour cannot be extracted.

Extension `bazaar`:

15. The example schemas for HTTP inputs use `additionalProperties: false` on `input` without declaring `pathParams`; an RS that follows those examples and also emits `info.input.pathParams` for a dynamic route produces an `info` that fails its own `schema` (BAZAAR-19 vs BAZAAR-40).
16. `output.example` is typed `any` in the field table, `{ "type": "object" }` in the HTTP example schemas and `{}` in the MCP schema example; the `format` field appears in the table but in no example schema.
17. The service-metadata and `routeTemplate` validation rules are addressed to facilitators/SDKs ("soft-drop"); the spec never says an RS MUST emit conforming values, so a tester can only warn that a value would be dropped downstream.
18. "byte-identical 402 bodies" is unenforceable against a specific server (there is no reference body); only "absent, not null" is testable.
19. The `EXTENSION-RESPONSES` value is "base64-encoded" without specifying the alphabet or padding; examples use the standard alphabet with `=` padding.
20. `SettleResponse.extensions` ("server enriches via hooks") is mentioned only in the channel table; how the RS merges its own extension data with the facilitator's is not specified.
21. Whether a `PaymentPayload` whose `bazaar` echo differs from the advertised one (client tampering) must be rejected by the RS or merely dropped by the facilitator is not stated.

Extension `payment-identifier`:

22. The `id` charset rule (alphanumeric, hyphen, underscore) is not enforced by the advertised JSON schema (length only) and RS behaviour on a malformed `id` (400? ignore?) is unspecified.
23. The idempotency table is titled "Server Response" and uses HTTP statuses (409, 400); it is silent on how a facilitator signals the same outcomes on `/verify` and `/settle`.
24. "Same `id`, same payload" versus fingerprint binding: the table speaks of payload equality, the Request Binding section of a fingerprint that excludes the signature. Whether a retry with a fresh signature but identical fingerprint counts as "same payload" (cache hit) is left to interpretation; the fingerprint reading is the only one compatible with retries after a transient failure.
25. Scoping guidance ("scope the key by tenant, merchant, route") contradicts the fingerprint rule for the cross-route case: with route scoping the same `id` on another route is a new `id` (processed), with a global fingerprint that includes the path it is a conflict (409).
26. Whether an `id` observed on a request that later fails verification/settlement is stored (and therefore poisons retries) is unspecified.
27. Nothing says whether the RS must reject an `id` when the extension was not advertised, nor whether the cached response must be byte-identical or only semantically equal.

Extension `sign-in-with-x`:

28. `x402Version` is the string `"2"` in every SIWX example; the core spec uses the integer `2`.
29. `supportedChains` is a third top-level member of the extension object next to `info`/`schema`, which the core `info`+`schema` pattern does not foresee; clients echoing "at least the info received" may or may not carry it.
30. The advertised `schema` describes the client proof (it requires `address` and `signature`), so the server's own `info` does not validate against it, contrary to the core definition of `schema` as validating `info`.
31. The proof example contains `signatureScheme`, which is neither in the client proof field table nor in the schema; `type` and `chainId` are also copied from `supportedChains[]` into the proof without this being stated in the table.
32. Base64 alphabet and padding of `SIGN-IN-WITH-X` are unspecified (example is unpadded standard alphabet with length divisible by 4, so it does not disambiguate).
33. Where the machine-readable `invalid_siwx_*` codes are carried (HTTP status, `PaymentRequired.error`, a body field, a header) is not stated; nor is the status code for a failed SIWX check (presumably a new 402 challenge).
34. The `invalid_siwx_domain_mismatch` row says "does not match the request host" and `invalid_siwx_uri_mismatch` says "does not start with the expected resource origin", whereas the normative rules require matching the configured public origin exactly; the table wording is looser than the rule.
35. Nonce handling: the server "MUST generate" the nonce and "SHOULD track used nonces", but nothing requires the server to check that a presented nonce was actually issued by it (a client could mint a fresh nonce per request and defeat replay tracking that only records seen nonces). Nonce lifetime/pruning is also unspecified.
36. The SIWE/SIWS templates omit the `Not Before:` and `Request ID:` lines defined by EIP-4361 even though `notBefore` and `requestId` are challenge fields; the exact reconstruction when those are present is undefined, as is the layout when `statement` or `resources` is absent.
37. Step 4 (payment history) is "application-specific": what "previously paid for the requested resource" means (same URL? same route? any resource on the server? time-boxed?) is undefined, and the success response shape (with or without `PAYMENT-RESPONSE`) is not described.
38. Interaction with `PAYMENT-SIGNATURE` on the same request (both headers present; SIWX valid but address never paid) is unspecified.
39. `invalid_siwx_chain_id` is described as "not a valid CAIP-2 EVM identifier", leaving the code for a malformed Solana `chainId` undefined.

Extension `offer-receipt`:

40. §3.1.1 requires `network` to be `eip155:<chainId>` and `payTo` to be an EVM address for `format = "eip712"`, but §3.2 (v0.6) explicitly makes EIP-712 "chain-agnostic" and usable for Solana; the two clauses contradict each other.
41. §4.3/§5.3 say unused optional fields MUST be `0`/`""` under EIP-712 while §4.5/§5.5 say the payload "MUST be used exactly as transmitted" and must not be reconstructed; it is unclear whether an EIP-712 payload may omit `validUntil`/`transaction` (verifier fills the sentinel) or must transmit the sentinel explicitly. The EIP-712 examples always transmit `"transaction": ""`; the offer schema does not list `validUntil` as required.
42. The JWS receipt example in §5.4 decodes to a payload without `transaction`, whereas the §6.7/§6.8 JWS examples include `"transaction": ""`; the spec does not say whether JWS payloads use the sentinel or omission.
43. The spec calls the settle response `SettlementResponse`; the core spec calls it `SettleResponse`.
44. Nothing states that `resourceUrl` must equal `resource.url` (v2) or `accepts[].resource` (v1), nor that `payer` must equal `SettleResponse.payer`; both are only implied by the examples.
45. `did:web` resolution and the DNS TXT `_controllers` format are described as "common approaches", not requirements; a tester cannot fail an RS whose key is authorised by an out-of-band registry it cannot see.
46. The JWS `alg` set is open ("e.g., `ES256K`, `EdDSA`"); `kid` "DID URL" is not constrained to a DID method the tester can resolve.
47. No rule says `validUntil` must be in the future when the offer is issued, nor whether `validUntil` should relate to `maxTimeoutSeconds`.
48. The receipt is "returned only on success" but the spec does not say what happens on `settlement_pending` (non-terminal) or when the handler fails after a successful settlement under `upfront`.
49. The `schema` member of `extensions["offer-receipt"]` appears in the examples only; the extension text never mentions it, so its presence alongside `info.receipt` in the settle response rests on the core §5.1 pattern.
50. The EIP-712 payload `version` is `uint256` on-chain but a JSON number on the wire; large values would not round-trip in JavaScript, though only `1` is defined today.
