# x402 v2 requirements, canonical merged inventory

Sources: three independent, spec-only extractions merged by clause and requirement text (never by original ID): `requirements-claude.md` (core specification and HTTP transport), `requirements-claude-part2.md` (`exact`, `exact` on EVM, `bazaar`, `payment-identifier`, `sign-in-with-x`, `offer-receipt`) and `requirements-codex.md` (all eight files, written by another agent). Spec snapshot: `x402-foundation/x402` upstream commit `59f1347a` (`spec/UPSTREAM_COMMIT`), files under `spec/`. Where the extractions disagreed, the spec text decided; every such case is listed under "Divergences between the extractions". No implementation was consulted.

Legend.

- **ID**: stable, `PREFIX-NNN`, one counter per spec file, in the order of the spec text. Do not renumber; append.
- **Role**: `RS` resource server, `C` client (including the conformance tool when it acts as one), `F` facilitator (including a Bazaar catalog or discovery service it hosts), `ANY` (all parties, a mechanism or spec document author, an SDK, or an external verifier of signed artifacts). Combinations such as `RS/F` mean both.
- **Level**: `required` (MUST, MUST NOT, SHALL, "Required" in a field table, prescriptive prose such as "must", "is", "always"), `recommended` (SHOULD, SHOULD NOT, "should"), `optional` (MAY, "may", examples, choices the text leaves open). A requirement marked `required` that only applies when a capability is offered is conditional: absence of the capability is not a failure.
- **Source**: how strong the textual basis is: `explicit-must` (uppercase RFC 2119 keyword), `field-table` (Required/Optional column of a table), `prose` (lowercase imperative or definitive wire contract without a keyword), `example` (established only by an example or an illustrative note).
- **Clause**: section reference and a short quote from the pinned file.
- **Observability**, for a black-box test of a resource server: `probe` (no funds: a 402 fetch, a throwaway key, a malformed request, a read-only RPC call), `paid` (one real testnet payment), `facilitator` (only if the tool hosts the facilitator the server talks to), `witness` (additionally needs the tool's controlled backend behind the server, for ordering and non-execution claims), `n/a` (not observable from outside: client, facilitator-internal, document or internal-state obligations; the tool must itself comply when acting as client).
- **Provenance**: the original IDs, `claude` for the two Claude files, `codex` for the Codex file. A row present in only one extraction keeps just that one.

## Divergences between the extractions

Each item names the merged row, the two readings, the arbitration and the spec quote that decides it. Agreements phrased differently (for example `MUST(implicit)` versus `MUST (prose)`) are not listed.

1. **CORE-029, EVM-010 (EIP-3009 payload fields), level.** claude CORE-5.2-03 `MUST(implicit)`; codex CORE-5.2-06 `Example` ("not a universal shape"). Spec §5.2.2: "For example, with exact EVM scheme, this includes:" followed by two tables whose Required column reads Required for every field, and the EVM file §1 Phase 1 "The `payload` field must contain". Arbitration: `required`, source field-table, conditional on the mechanism being `exact`/EIP-3009; codex's caution is kept in the requirement text (select the mechanism before validating). The encodings (decimal strings, 0x-hex nonce) remain example-only, as claude EXACT-EVM-10 noted.
2. **CORE-060 (multiple settles), level and reading.** claude CORE-7.2-02 `MUST(implicit)`: "for `exact` authorization a single settle per payment"; codex CORE-7.2-03 `MAY`: "Multiple settles are not universally forbidden". Spec §7.2 note: "`/settle` MAY be invoked more than once for a single payment (for example, the `escrow` flow ...). A scheme defining multiple settles MUST specify how the facilitator distinguishes them". Arbitration: `optional` is the level of the clause; the number of `/settle` calls is reported as a fact and never judged (D7): a retry is neither a new stage nor a new transfer. The observable violation is a second success receipt naming a new transaction (EXACT-020, CORE-072), not a second call.
3. **CORE-070 (standard error codes), level.** claude CORE-9-01 `MUST(implicit)` ("when a standard condition occurs, the standard code is used"); codex CORE-9-01 `MAY` ("not a universal exact-message mandate"). Spec §9: "defines standard error codes that may be returned by facilitators or resource servers". Arbitration: `optional` for the use of the vocabulary; a listed code used with a different meaning is still a violation (both extractions agree on that half).
4. **CORE-072, CORE-073 (replay and time windows), role and scope.** claude CORE-10.1-01/02 role RS/F, general; codex CORE-10-01 role CL/F, "EIP-3009 ... Do not generalize this mechanism's nonce to all x402". Spec §10.1 lists "EIP-3009 Nonce: Each authorization includes a unique 32-byte nonce" and "EIP-3009 contracts inherently prevent nonce reuse". Arbitration: the nonce mechanism is EIP-3009-specific (role RS/F/C, scope noted in the row); the observable server-side consequence, no second settlement and delivering the cached response again is allowed and reported as information (D8); only a second success receipt with a new transaction counts.
5. **HTTP-006 (402 after failed settlement), level and reading.** claude HTTP-06 `MUST(implicit)` from the failure example; codex HTTP-EXAMPLE-01 `Example`: "Do not require fresh payment terms on every 402". Spec Error Handling table: "Payment Failed \| 402 \| Payment verification or settlement failed" (prose table); the Example (Failure) shows `PAYMENT-RESPONSE` and no `PAYMENT-REQUIRED`. Arbitration: the 402 status and the failure receipt are `required` (table); whether a fresh `PAYMENT-REQUIRED` accompanies it is example-only and neither required nor forbidden.
6. **HTTP-008, HTTP-009 (response bodies), level.** claude HTTP-08 `MUST(implicit)` ("the tool must not require protocol data in bodies; body-only signalling is non-conformant"); codex HTTP-BODY-01 `MAY` ("HTML, JSON, text, empty ... are allowed"). Spec Response Body: "Response bodies are a server implementation concern. All x402 protocol information is communicated through headers". Arbitration: both readings hold and were split: header carriage is `required` (HTTP-008), body content is `optional` (HTTP-009).
7. **HTTP-004 (`PAYMENT-SIGNATURE`), role.** claude HTTP-04 role C; codex HTTP-PAYLOAD-01 role CL/RS. Spec: "Clients send payment data using the `PAYMENT-SIGNATURE` HTTP header". Arbitration: C/RS, since the server must read the payload from that header for the transport to work; this is what makes the row probe-observable.
8. **EVM-031 (Permit2 412), role and observability.** claude EXACT-EVM-31 role "facilitator (relayed by resource server)", probe at the client-facing hop; codex EVM-PERMIT2-08 role F, "N/direct F; C can test RS propagation where specified". Spec §2 Phase 3 step 2: "Return `412 Precondition Failed` (Error Code: `PERMIT2_ALLOWANCE_REQUIRED`)". Arbitration: role F as written; the emitting hop is unspecified (ambiguity E3), so the probe expectation is recorded as "412 and the code at the client-facing hop, else report which hop emitted what" rather than a hard failure.
9. **BAZAAR-001 (advertising Bazaar), level.** claude BAZAAR-01 `MUST(implicit)` on key and location; codex BAZAAR-DECL-01 `MAY` ("Missing Bazaar is not a core failure"). Spec: "A resource server advertises its endpoint specification by including the `bazaar` extension in the `extensions` object of the 402 Payment Required response". Arbitration: `required` conditional on advertising the extension; the extension itself is optional. Both statements are in the row.
10. **BAZAAR-028 (`info` validates against `schema`), role.** claude BAZAAR-19 derives an RS obligation (`MUST(implicit)`, probe); codex BAZAAR-SCHEMA-07 keeps it on F ("N for RS-only"). ## Ambiguities and gaps

Merged and deduplicated from the 12 core/HTTP items, the 50 scheme/extension items and the 18 Codex items. Encode these as `optional`, warnings or `cannot-assess`, never as failures without a documented interpretation; keep the item number in the evidence when a verdict depends on it.

### Core specification

1. §5.1.2 `accepts` (C:117): required array with no `minItems`; no `additionalProperties: false`, no `amount` grammar, no numeric bounds or header size limit anywhere in the core. A 402 with an empty or unusable `accepts` is structurally valid but not payable: report "no payable offer", do not invent a MUST. (claude core 2; codex A01)
2. §5.2.2 `accepted`: how strictly it must match an offered entry (equality, subset, `extra` handling) is undefined. (claude core 3)
3. §5.1.2 `maxTimeoutSeconds`: "maximum time allowed for payment completion" is tied to no observable server behaviour and, in the EVM binding, to no signature window; only the Stellar and Starknet paragraphs bind expiry to it. (claude core 6; claude part 2 item 10)
4. §10.1: replay protection is stated as a security property of EIP-3009, not as a status code or a general x402 rule; the observable requirement is "not settled twice, not delivered twice as newly paid", not a particular status (no mandatory 409 on a bare replay). (claude core 8; codex A02, CORE-10-01)
5. §9 `settlement_pending`: server behaviour toward the client (status, `PAYMENT-RESPONSE` content, retry semantics, whether the resource is delivered or withheld) is unspecified beyond the receipt content; the EVM file defers to the core and the offer-receipt file says nothing about receipts on a pending outcome. Delivering or withholding are both defensible; a fresh challenge inviting a second signature is the behaviour to flag. (claude core 9; claude part 2 items 11 and 48)
6. HTTP method of the protected resource (GET versus POST) is out of scope; the tool needs it as input, and a no-funds probe does not guarantee freedom from application side effects. (claude core 10; codex evidence mode A)
7. Nothing in the core or HTTP transport defines a `/.well-known` manifest; tools checking one check something outside these documents. (claude core 12)
8. §8: the list response envelope (`x402Version`, `items`, `pagination{limit, offset, total}`) exists only in an example, while §8.3 has a Required table for item fields; the Bazaar file says search "mirrors" the list with a `resources` array. Keep separate list/search parsers and label the assumed envelope. §8.3 `type` "currently http" does not exclude the Bazaar's MCP type. (codex A10, BAZAAR-DISCOVERY-04)
9. §12 and the scope note: session passes, tokens, purchase-status endpoints, reconciliation APIs, retention durations and custom settlement headers are outside the normative core; no prior implementation's contract may fill a spec gap. (codex A18, CORE-12-01)
10. External normative dependencies (CAIP-2 grammar, EIP-712, EIP-3009, Permit2, EIP-4361, SIWS, JCS, JSON Schema 2020-12, MCP `Tool.inputSchema`) are referenced, not copied; structural checks or a library's acceptance are narrower evidence than full validation. (codex A15)
11. §5.2.2 introduces the EIP-3009 payload tables with "For example"; their Required column applies to that mechanism only (divergence 1).

### HTTP transport

12. The base64 variant is never named for `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE`, nor for `EXTENSION-RESPONSES` (core §7.2.1, Bazaar) or `SIGN-IN-WITH-X`; every example uses the standard alphabet with `=` padding (the SIWX example is unpadded only because its length is a multiple of 4). Decode leniently (standard and URL-safe, padded or not), report the variant, never fail on it. (claude core 1; claude part 2 items 19 and 32)
13. Malformed `PAYMENT-SIGNATURE`: the error table maps "Invalid Payment" to 400 and "Payment Failed" to 402; a server answering 402 with a new challenge to a malformed header is defensible. Treat 400 as expected, 402-with-challenge as acceptable-with-note, 200 or 500 as failures. Distinguish malformed syntax from failed verification. (claude core 4; codex A02)
14. Whether the 402 after a failed verification or settlement must also carry a fresh `PAYMENT-REQUIRED` is not stated; the example carries none (divergence 5). (claude core 5; codex A02)
15. Header casing: HTTP header names are case-insensitive; the spec's upper case is presentation. Never fail on casing. (claude core 7)
16. The 402 body: the example shows `{}` with `Content-Type: application/json`; no requirement exists. The Bazaar channel table calls `PaymentRequired.extensions` the "402 response body", which is stale wording against the canonical header (see item 44). (claude core 11; codex A05)
17. The error table does not cover application success codes other than 200, non-terminal settlement, cached replay responses or arbitrary backend 5xx; name the tested category and interpretation. (codex A02, HTTP-ERROR-04, HTTP-ERROR-05)

### Scheme `exact`

18. `maxAmountRequired` (SVM amount exactness, X:66) is the v1 field name; v2 `PaymentRequirements` uses `amount`. Compare against `amount`; do not add legacy fields to v2 schemas. (claude part 2 item 1; codex A17)
19. The client-submitted (payment-proof) family is fully specified in the abstract but no in-scope mechanism instantiates it; EXACT-022 to EXACT-034 cannot be exercised against an EVM-only server. (claude part 2 item 2)
20. "this specification defines no refund" under `upfront`: failure after charge is explicitly unremedied; the tool records settlement and resource outcome separately and does not judge. (claude part 2 item 3; codex EXACT-FLOW-05)
21. "`authorization` SHOULD be preferred wherever the asset transfer method permits it" has no observable criterion for when `upfront` is justified; only a warning is defensible. (claude part 2 item 4)
22. The SVM, Stellar, TON and Starknet paragraphs (X:62-90) are conditional on those networks and their binding documents are not in this snapshot; advertised non-EVM mechanisms are cannot-assess, not conformant because their core JSON passed. (codex exact section note; claude EXACT-49)

### Scheme `exact` on EVM

23. The `authorization` and `permit2Authorization` field names, JSON types and encodings (decimal strings, 32-byte hex nonce, 0x addresses) are established only by examples; there is no normative field table in the EVM file (the core §5.2.2 table covers EIP-3009 names and types only). The Permit2 example JSON is invalid (missing comma, `//` comment, trailing comma); examples carry shortened signatures and placeholders and must never be used as positive cryptographic vectors. The status of non-65-byte smart-wallet signatures is unclear. (claude part 2 item 5; codex A04, EVM-3009-01)
24. Permit2 verification lists no check that `permit2Authorization.spender` equals the canonical proxy nor that `witness.to == payTo`, although both are described as the security mechanism; the failure codes for those cases are undefined. (claude part 2 item 6)
25. Permit2 step 2 says "Return `412 Precondition Failed` (Error Code: `PERMIT2_ALLOWANCE_REQUIRED`)", but `/verify` returns a JSON `isValid`/`invalidReason`, not HTTP statuses, and the core vocabulary is lowercase snake_case; which hop emits the 412 and where the code string travels is unclear (divergence 8). 26. 27. No explicit statement that `authorization.to` must equal `payTo` for EIP-3009; implied only by the core code `invalid_exact_evm_payload_recipient_mismatch` and by transfer correctness. (claude part 2 item 9)
28. `extra.assetTransferMethod` is "required" for `permit2` and `erc7710` but unverifiable from outside: an entry lacking it is EIP-3009 by definition. (claude part 2 item 12)
29. The canonical Permit2 address is given only by external link; the proxy address is inline and pinned to this snapshot. (claude part 2 item 13; codex EVM-ANNEX-01)

### Scheme `exact` on Solana

72. `extra.feePayer` is required by the field list ("requires the following inside the `extra` field") and by the flow, but no RFC 2119 keyword says so; the tool treats it as `required` with source `prose`.
73. The receipt's `payer` is shown as the fee payer in the Solana example while the core spec calls it "the payer's wallet address": an example, not a rule; a server that needs the paying wallet is safer with the `/verify` payer. The tool checks nothing about it.
75. The generic `exact` text asks for atomic deduplication of duplicate settlements on the facilitator side while the Solana file recommends a local cache with a TTL; the obligation stays with the facilitator, the tool judges a resource server on "not settled twice" only (D4).
74. The `upfront` flow is recommended for slow handlers without a threshold; the tool reports the flow offered.

The example HTTP schemas set `additionalProperties: false` on `input` without declaring `pathParams`; a server copying them and emitting `info.input.pathParams` for a dynamic route fails its own `schema` (BAZAAR-028 versus BAZAAR-052). Validate the actually advertised schema, not a copied example. (claude part 2 item 15; codex A11)
33. `output.example` is typed `any` in the table, `{"type": "object"}` in the HTTP example schemas and `{}` in the MCP example; `format` appears in the table but in no example schema; the `body` table allows object/string while the POST example schema is object-only. (claude part 2 item 16; codex A11)
34. The service-metadata and `routeTemplate` validation rules are addressed to facilitators and SDKs ("soft-drop"); the spec never says a server MUST emit conforming values, so the tool can only warn that a value would be dropped downstream (the core table limits, CORE-016 to CORE-018, remain server obligations). Do not turn a consumer sanitation rule into rejection of the whole payment. (claude part 2 item 17; codex A16)
35. "byte-identical 402 bodies" is unenforceable against a specific server; only "absent, not null" is testable. (claude part 2 item 18)
36. `SettleResponse.extensions` ("server enriches via hooks") appears only in the channel table; how the server merges its data with the facilitator's is unspecified. (claude part 2 item 20)
37. Whether a `PaymentPayload` whose `bazaar` echo differs from the advertised one must be rejected by the server or merely dropped by the facilitator is not stated. (claude part 2 item 21)
38. `$ref`/`$id` "same-document JSON Pointer fragments (starting with `#`)": not every `#fragment` is a JSON Pointer; the `routeTemplate` regex and the "non-empty" rule also differ on a bare `/`. Implement a documented literal interpretation and mark edge cases cannot-assess. (codex A12)
39. Bazaar says clients "are expected to echo" and omission only disables cataloging, whereas core §5.1.2 says the client "must include at least the info received"; reconcile as: core governs what an echo must contain, Bazaar governs the consequence of no echo. (codex BAZAAR-ECHO-01)
40. The channel table places `PaymentRequired.extensions` in the "402 response body"; the HTTP transport and core make the `PAYMENT-REQUIRED` header canonical and the body implementation-specific. Validate the extension inside the decoded header. (codex A05)

### Extension `payment-identifier`

41. The `id` charset rule is not enforced by the advertised schema (length only) and server behaviour on a malformed `id` (400, ignore) is unspecified; "alphanumeric" is read as ASCII. (claude part 2 item 22; codex PID-FORMAT-02)
42. The idempotency table is titled "Server Response" and uses HTTP statuses (409, 400) while the extension may be consumed by the server, the facilitator or both; how a facilitator signals the same outcomes on `/verify` and `/settle` is silent. Select the consumer profile before claiming server-side caching (divergence 12). (claude part 2 item 23; codex A06)
43. "Same `id`, same payload" versus fingerprint binding: the table speaks of payload equality, the Request Binding section of a fingerprint that excludes the signature; whether a retry with a fresh signature but identical fingerprint is a cache hit is left open. The fingerprint reading is the only one compatible with retries after transient failure. (claude part 2 item 24; codex A06)
44. Scoping guidance ("scope the key by tenant, merchant, route") contradicts the fingerprint rule for the cross-route case: with route scoping the same `id` on another route is new (processed), with a global fingerprint including the path it is a conflict (409). (claude part 2 item 25)
45. Whether an `id` seen on a request that later fails verification or settlement is stored (poisoning retries) is unspecified, as is any cache retention duration. (claude part 2 item 26; codex PID-IDEMPOTENCY-02)
46. Nothing says whether the server must reject an `id` when the extension was not advertised, nor whether the cached response must be byte-identical or only semantically equal. (claude part 2 item 27)
47. `required` has "Default: `false`" but the example schema lists `required` in its `required` array; treat omission as the documented default and note the example divergence. (codex A06, PID-INFO-01)

### Extension `sign-in-with-x`

48. `x402Version` is the string `"2"` in every SIWX example; the core uses the number 2. Prefer the core field table. (claude part 2 item 28; codex A04)
49. `supportedChains` is a third top-level member next to `info`/`schema`, which the core `info`+`schema` pattern does not foresee; clients echoing "at least the info received" may or may not carry it. (claude part 2 item 29)
50. The advertised `schema` describes the client proof (it requires `address` and `signature`), so the server's `info` does not validate against it, contrary to the core definition of `schema`; a generic "validate every `info` against its `schema`" check would reject the spec's own example. (claude part 2 item 30; codex A03)
51. The proof example contains `signatureScheme`, which is in neither the proof table nor the schema; `type` and `chainId` are copied from `supportedChains[]` into the proof without the table saying so. (claude part 2 item 31)
52. Where the machine-readable `invalid_siwx_*` codes are carried (HTTP status, `PaymentRequired.error`, body, header) is not stated, nor the status code for a failed SIWX check (presumably a new 402 challenge). (claude part 2 item 33)
53. The error table says `domain` "does not match the request host" and `uri` "does not start with the expected resource origin", looser than the normative configured-origin exact-match rules; use the strongest explicit clause. (claude part 2 item 34; codex A14)
54. Nonce: the server "MUST generate" it and "SHOULD track used nonces", but nothing requires checking that a presented nonce was actually issued by the server (a client minting fresh nonces defeats seen-nonce tracking); nonce lifetime and pruning are unspecified; do not require a particular store. (claude part 2 item 35; codex A14)
55. Temporal checks: equality at the boundaries, allowed clock skew and the default maximum age versus a configured one are incompletely specified; declare the clock and age policy, treat near-boundary observations as inconclusive. (codex A14, SIWX-VERIFY-04/06)
56. The SIWE/SIWS templates omit the `Not Before:` and `Request ID:` lines EIP-4361 defines although `notBefore` and `requestId` are challenge fields; the layout when `statement` or `resources` is absent is undefined; the full EIP-4361 and SIWS grammars are external. (claude part 2 item 36; codex SIWX-MESSAGE-01)
57. Step 4 (payment history) is "application-specific": what "previously paid for the requested resource" means (same URL, same route, any resource, time-boxed) is undefined, and the success response shape (with or without `PAYMENT-RESPONSE`) is not described (divergence 14). (claude part 2 item 37; codex SIWX-HISTORY-01)
58. Interaction with `PAYMENT-SIGNATURE` on the same request (both headers present; SIWX valid but the address never paid) is unspecified. (claude part 2 item 38)
59. `invalid_siwx_chain_id` is described as "not a valid CAIP-2 EVM identifier", leaving the code for a malformed Solana `chainId` undefined. (claude part 2 item 39)

### Extension `offer-receipt`

60. §3.1.1 requires `network` `eip155:<chainId>` and an EVM `payTo` for `format = "eip712"`, but §3.2 (v0.6, "Make EIP-712 chain-agnostic") explicitly allows non-EVM networks such as Solana, and the receipt payload has no `payTo` at all. The EVM profile is unambiguous; mark the broader case unresolved rather than failing non-EVM artifacts or requiring `receipt.payTo`. (claude part 2 item 40; codex A08)
61. §4.3/§5.3 say unused optional fields MUST be `0`/`""` under EIP-712 while §4.5/§5.5 say the payload "MUST be used exactly as transmitted"; whether an EIP-712 payload may omit `validUntil`/`transaction` (verifier fills the sentinel) or must transmit it is unclear. The EIP-712 examples always transmit `"transaction": ""`; the example offer schema does not list `validUntil` as required. (claude part 2 item 41)
62. The §5.4 JWS receipt example decodes to a payload without `transaction`, whereas the §6.7/§6.8 JWS examples include `"transaction": ""`; sentinel versus omission for JWS is unsaid. (claude part 2 item 42)
63. The extension calls the settle response `SettlementResponse`; the core §5.3.2 table calls it `SettleResponse` (the core itself uses both names). (claude part 2 item 43)
64. Nothing states that `resourceUrl` must equal `resource.url` (v2) or `accepts[].resource` (v1), nor that `payer` must equal `SettleResponse.payer`; both are implied by examples only. (claude part 2 item 44)
65. `did:web` resolution and the DNS TXT `_controllers` format are "common approaches", not requirements; a server whose key is authorised by an out-of-band registry the tool cannot see is cannot-assess, not failing (divergence 15). (claude part 2 item 45; codex OFFER-AUTH-02)
66. The JWS `alg` set is open ("e.g., `ES256K`, `EdDSA`") and `kid` "DID URL" is not constrained to a resolvable DID method; an unsupported algorithm or method is an explicit cannot-assess outcome. (claude part 2 item 46; codex OFFER-JWS-01)
67. No rule says `validUntil` must be in the future when the offer is issued, nor how it relates to `maxTimeoutSeconds`. (claude part 2 item 47)
68. The `schema` member of `extensions["offer-receipt"]` appears in examples only; its presence next to `info.offers` and `info.receipt` rests on the core §5.1 pattern. (claude part 2 item 49)
69. The EIP-712 payload `version` is `uint256` in the struct but a JSON number on the wire; large values would not round-trip in JavaScript, though only `1` is defined. (claude part 2 item 50)
70. §2 declares wire shape and placement unstable while behavioural rules are normative; pin the exact revision and placement profile in reports, "latest compatible" is not a reproducible target. (codex A09)
71. JCS (RFC 8785) for JWS payload canonicalisation is a normative external dependency to pin before claiming full validation. (codex ARTIFACT-CANON-01)

Ambiguity count: 75.
